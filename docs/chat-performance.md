# Chat 性能优化（审查修订版）

2026-10-19。以 `parallel` 分支恢复后的代码为基线。用户要求保留本文件、丢弃其余未提交改动，再按修订方案实现。原文备份在本机 `/private/tmp/nomi-sub-chat-performance-original.md`；该路径不是应用依赖。

## 1. 确认的问题与原方案的修正

代码可以确认以下重复工作，但没有实测之前，不给出卡顿耗时或内存占用结论：

- `AskView.conversation` 原先用 `VStack`，打开历史时会创建所有轮次的富文本和 HTML 网页。底部滚动锚点不等于懒加载。
- 草稿、历史和 `pendingAnswer` 原先在同一 SwiftUI 视图中读取，输入或流式更新会重新进入历史的构建路径。`ChatTurn` 声明 `Equatable` 本身不会自动建立视图更新边界，必须使用独立子视图和显式 `.equatable()`。
- `AnswerBody.body` 每次都解析 Markdown，再调用会重新解析一遍的 `ChatFiles.export`，还会在主线程检查/写入导出文件。
- `AnswerInline.render` 原先逐字符创建富文本并设置字体和颜色。连续普通文本应按一整段构建，保留所有格式标记和链接的识别。
- `CiteText.sizeThatFits` 每次都重新设置容器宽度并调用 `ensureLayout`。同样的文本、主题和宽度应复用量过的尺寸；宽度实际变化时需要重新排版，不能用“相差 8 pt 以下忽略”掩盖换行或公式宽度变化。
- HTML 卡片原先各自持有 `WKWebView`，离屏不一定停止脚本和高度更新。

修正原文中的几个不成立的保证：

1. **WKWebView 数量不等于 WebContent 进程数量。** 共用非持久化数据存储可以避免每张卡单独创建存储会话，但不能保证一个进程，或限制 WebKit 的进程总数。我们限制的是本应用创建的网页视图实例最多 3 个，不使用已过时的 `WKProcessPool`。
2. **LazyVStack 的预取范围由 SwiftUI 决定。** 不能保证正好是视口上下各一屏。进一步的快速翻阅检查暴露了高度估算/异步内容替换导致空白的风险，因此最终实现使用 macOS 原生 `NSTableView` 复用行，而非只换成 LazyVStack。HTML 另根据原生滚动视口与卡片几何关系判断预取，不依赖 SwiftUI 惰性视图的生命周期。
3. **不能固定首次上报的 HTML 高度。** 用户交互、字体布局、窗口宽度变化都可能改变高度；保留动态上报，合并高频消息、忽略约 1 pt 的变化，并限制异常高度。
4. **PNG 快照不保存 JS 状态。** 回收网页后再加载，会重新初始化脚本、表单和动画。快照保留最后的外观，并不是完整交互状态恢复。当前挂载中的网页不因流式更新或普通父视图刷新重新加载。
5. **磁盘快照不是这次优化的前提。** 原方案的 `snapshot.txt` 只有高度，缺少 HTML 内容、宽度、倍率和主题的失效条件；原代码也没有“删除会话就删除 HTML 导出文件”的逻辑。为修复卡顿，这轮不增加磁盘快照格式、共享文件引用计数或后台清理协议，改为有上限的进程内快照缓存。重启后只重新加载当前可见的演示，不提前恢复全部网页。
6. 不预设“JSON 一定不慢”。目前会话加载发生在初始化，页面切换主要重复工作在渲染；本次不改存储格式或模型上下文。若后续测量指向启动读取或保存，再单独优化存储。

## 2. 目标和范围

- 长历史按需创建消息视图，同时预解析邻近消息；快速向上翻也不能用整屏空白换性能。
- 输入草稿不使历史 Markdown 重新解析；流式更新仅作用于当前回答。
- Markdown 结构提前在后台解析；冷缓存的可见行允许同步解析一次结构，保证首帧有正文。HTML 文件导出始终在后台进行，不为导出重复解析正文。
- 网页实例最多 3 个；不可见演示使用静态快照/占位和已知高度。
- 保留引用、右键菜单、文本选择、公式、代码、表格、图片、文件打开/保存、隐藏工具调用、停止回答与恢复草稿。
- 不改提示词、历史上下文预算、模型接口和 Rust/MLX 推理速度；不放宽 HTML 安全检查与 CSP、外链/弹窗拦截。

这不是保证任意大小的单条回答都恒定耗时。懒加载粒度是轮次，单轮超长回答的富文本构建和数学公式仍有成本；流式节流降低频率，不会消除单次渲染成本。

## 3. SwiftUI 更新边界

`AskView` 保留页面、历史面板与范围面板。`ChatTranscript` 用原生 `NSScrollView + NSTableView` 创建和复用邻近行，每行使用一个 `NSHostingView` 保留现有 SwiftUI 消息样式。完整历史留在数据层，只有附近的行创建富文本/网页。

监听滚动裁剪视图的边界变化，在阅读方向提前准备 6 轮、反方向保留 2 轮，额外视图最多 8 轮。这些是真实的 SwiftUI/TextKit 消息视图，已完成文字排版并提前更新行高；按文档中的真实位置挂载在视口外，让图片和视口附近的 HTML 也能提前加载。预备工作逐轮执行，每轮之间让出主线程，避免一次创建整个历史。每个邻近轮次按 ID 保留唯一的消息视图，测量请求与实际显示共用它，不让通用复用池覆盖仍在准备的消息。进入视口时使用同一个视图，不再创建一份新正文。离开邻近范围、且表格已经释放该行后回收它；切换会话、主题或窗口宽度时取消过期工作。

首次打开滚到底部；之后高度变化时记录首个可见轮次 ID 和行内偏移，修改行高后恢复到同一个阅读位置。只有距离底部不超过 2 pt 才认为读者在跟随最新答案；原来的 80 pt 阈值会把刚开始向上翻的读者拉回底部。位置修复产生的滚动不当作用户改变阅读方向。窗口宽度、主题或语言环境改变时使相应高度失效，旧排版代次的迟到高度回调不再生效；主题、语言和减少动态效果显式传入每个原生行的 SwiftUI 根视图。

`ChatTranscript.sizeThatFits` 只返回父视图建议的视口大小，不使用文档的 fitting size 决定页面/窗口高度。行宿主采用显式尺寸，关闭自动 intrinsic size 与窗口安全区反馈。真实 `AppShell` 验证曾暴露预加载导致文档尺寸影响窗口、反复更新约束的异常，必须隔离视口与文档的测量；只验证独立 `AskView` 不足以覆盖它。

- `ChatTurnRow` 接收已完成的 `ChatTurn`，显式比较轮次值及模型对象身份，再使用 `.equatable()`。正文、引用、图片或错误变化时会更新；准备图示的状态保留在轮次外部，不会被相等比较屏蔽。
- `ChatPendingTurn` 单独读取 `pendingAnswer`、`pendingCitations` 和待发送图片。父视图不读取不断变化的回答文本。
- `ChatComposer` 单独读取 `ChatComposerState` 中的草稿、输入焦点和图片提示。示例按钮通过这个状态对象填入草稿，父视图不订阅草稿内容。发送、停止、粘贴/拖放图片、删除图片、取消后恢复草稿保持原逻辑。
- 不再在每次进入 Chat 时同步扫描模型目录。模型库初始化、下载完成、删除和模型切换原本就更新已安装集合。

相等比较只能隔离父视图输入变化，不能屏蔽子视图实际订阅的环境/状态变化；深浅色主题变化仍需要重新渲染。

## 4. 解析与文本排版

新增 `AnswerPreparation`：

1. 在串行后台 actor 中解析一次 `AnswerDocument.Piece`。新前缀到来会取消旧任务；排队后已取消的任务在开始时退出，避免长答案造成多个解析任务并发抢占 CPU。
2. 将同一份 pieces 直接交给 `ChatFiles.export(pieces:)`，避免第二次解析和主线程文件操作。
3. 完成后回到主线程更新视图；取消/过期的请求不应用结果。解析任务在开始、导出前后检查取消。
4. 完成答案的结构和文件映射用 `NSCache` 缓存，最多 64 项，成本预算约 8 MiB（文本大小的估算，不是总进程内存保证）。不缓存每一个流式前缀，以免挤掉完成的答案。

进入会话时低优先级预解析最近 24 轮。原先仅预解析邻近消息的结构，仍把富文本视图创建和行高测量留到了可见时，不能消除边滚动边排版的停顿。现在邻近预备行先等待该轮的结构和导出文件准备完成，再提前构建原生文字视图，遵守上一节的额外 8 轮上限。网页继续受 3 个实例的独立上限限制，可见消息优先于后台预取。

可见的已完成消息在冷缓存时，仅同步解析一次纯结构并立即完整排版，文件导出仍在后台进行；邻近预取通常让这一步直接命中缓存。这里有意不使用“先放一个很矮的旋转图标，再异步换成很高的历史正文”的做法，避免快速滚动时高度估算反复变化、出现空白或跳位。后台导出沿用首帧解析的 pieces，不重复解析，完成后补全文件链接。

流式回答首次后台解析尚未完成时，立即显示轻量正文预览，而非仅显示旋转图标。预览跳过代码围栏，避免把 HTML 和脚本直接闪给用户；纯 HTML 使用带说明的占位。已解析的流式前缀继续显示到新结果准备好。

结构缓存只含 pieces 和导出映射，因此用完整正文作为键；不缓存带主题/宽度的富文本。引用映射仍从当前正文与当前引用生成。文件名使用现有按内容摘要分目录的实现，不把不同 HTML 混在一起。

内联普通文本按连续片段建立富文本。代码、粗斜体、数学公式、引用、裸 URL 和不完整流式标记继续走现有解析分支。

`CiteText` 在自己的协调器中保存当前文本/主题/宽度对应的测量结果。**测量使用独立的 TextKit 存储、布局管理器和容器，不能使用屏幕上的 NSTextView 容器。** SwiftUI 会多次探测建议宽度，AppKit 也会修改显示视图的容器；共用容器会把窄宽度的测量高度缓存给宽视图，产生大量空白。显示 NSTextView 关闭自行垂直伸展，由 SwiftUI 设置测量后的高度。相同内容宽度复用尺寸；内容、主题、流式状态或宽度变化时重新装饰并清掉尺寸。公式使用实际建议宽度重新计算。不会把整轮高度强行固定，否则动态 HTML 和图片加载后会被裁切。遵循系统减少动态效果设置关闭流式淡入。

## 5. 流式合并

`ChatStreamUpdates` 接收的是累计全文，不是丢弃中间 token 的增量。

- 从首个待处理更新起，每 50 ms 最多提交一次最新全文（约 20 Hz），持续有 token 时也不会无限延后。
- 隐藏工具文本和引用的解析放在合并之后，减少扫描次数。
- 每轮请求完成后立即 flush，再使用后端返回的完整最终答案完成存储，不依赖最后一次定时器才能补全尾部。
- 出错或取消时丢弃待刷新内容；任务退出取消定时器，旧请求不能写入下一次回答。
- 后台结构解析仍可能按累计全文处理，所以不宣称“每帧扫描任意长度答案都很便宜”。

## 6. HTML 可见性与有界复用

每张卡片只有轻量 `DemoWebHost`、快照及高度。监听原生滚动裁剪视图的边界变化，在视口上下各约一屏的范围提前请求网页，优先保留离视口中心更近的卡片。原生视图尚未进入窗口时不分配网页，预取也必须遵守 3 个实例的总数限制。其他 SwiftUI 滚动容器中的回答仍可使用滚动可见性回调。

`DemoWebPool` 按需创建最多 3 个 `WKWebView`，共用一份非持久化 `WKWebsiteDataStore`。存储对象的语义参见 [Apple websiteDataStore 文档](https://developer.apple.com/documentation/webkit/wkwebviewconfiguration/websitedatastore)。

- 有空槽时直接挂载；需要腾出槽时，优先回收离视口中心更远的卡片。
- 如果同屏超过 3 张，剩余卡片显示快照，点击它可以优先激活，避免无法使用。
- 离开预取范围或退出页面时尝试获取快照，再把网页从宿主移除并载入空页，停止闲置脚本。实例留在池中复用。快照失败/超时也必须归还槽，不能把滚动锁住。
- 快照过程中槽仍占用数量，不能为等待快照而临时创建第 4 个网页。
- 初次加载期间保留已有快照，完成后才显示网页。所有延迟完成回调检查代次，旧加载/快照不会覆盖新宿主。
- 网页当前可见时继续响应交互和高度变化。高度脚本监听 border-box 尺寸以及 DOM 变动（包括 padding/子节点变化），以约 60 ms 的节流合并，连续变化也不会无限推迟；宿主进一步忽略微小变化，延后写入 SwiftUI 状态以避免在原生布局中同步改状态。
- 复用时保留原导航、响应、弹窗限制；`AnswerDocument` 的安全检查和 CSP 不变。

快照 API 是异步的，失败时使用已有快照或占位。参见 [Apple takeSnapshot 文档](https://developer.apple.com/documentation/webkit/wkwebview/takesnapshot(with:completionhandler:))。

## 7. 缓存生命周期

- 快照键包含轮次/图示身份（不同消息的交互画面不串用）、渲染 HTML 的 SHA-256（包含深浅色页面样式）、实际列宽（半点精度）和屏幕倍率。
- 位图长边目标不超过 2048 像素，快照缓存预算 64 MiB、最多 128 项；高度单独缓存最多 512 项。预算是驱逐依据，不是进程 RSS 上限。
- 缓存不写入磁盘；切页/切会话保留最近的缓存以加速返回，`NSCache` 可随内存压力释放，进程退出全部释放。删除会话不会留下新的磁盘快照文件。
- HTTPS 图片、用户上传照片沿用现有图片加载逻辑，不混入网页池。

## 8. 验证

编译应用；只运行与改动相关的解析/安全、流式合并、缓存与网页生命周期检查，不运行模型下载或长时间推理。

需要覆盖：连续更新合并、最终 flush、取消后无延迟写入；普通文本与中英混排、格式标记/引用/URL 不变；完整与未完成 HTML 的处理和沙箱不变；缓存结果不串正文；离屏释放及网页数量上限；返回长历史仍能显示底部、滚动到旧消息，流式尾部完整。

性能结果要区分代码保证和实际测量：实例上限、任务边界、缓存预算由实现约束；真实长对话的切页耗时、输入延迟和 WebKit 进程资源由运行验证，不把推测写成已测结果。

### 本次验证结果

- **上一轮对“没有空白”的判断无效。** 只检查 `NSTextView.visibleRect` 非空，无法证明字形出现在滚动视口里；在这里它甚至可能超出文本视图自身的边界。真实会话截图复现了单行字形只需 18 pt、文本框却占位 144–738 pt 的错误。这不是预取延迟，而是错误的文本高度。
- 改成独立 TextKit 测量后，同一份 18 轮会话表格高度从约 58,906 pt 降至 9,212 pt；另一份 7 轮会话从约 148,744 pt 降至 6,346 pt。修正前后均导出相同轮次的渲染截图和布局数据，确认段落间的异常空白消失。诊断产物只保留在本机临时目录。
- 28 项针对检查通过，包括 200 轮合成历史、反复跳到第 0/140/30/190 轮、退出后返回、尾部刷新/取消、HTML 高度变化及安全规则。初次稳定布局时只挂载附近 4 个回答文本视图，并未创建全部 200 轮的文本视图。快速跳转现在检查**实际字形矩形与滚动视口相交**，并用新建的 TextKit 布局核对每个文本框高度，误差不得超过 2 pt。
- 将文本排版实现临时还原为上一提交、运行同一条 200 轮回归检查，得到 13 项失败，包括实际 126 pt 的文本占位 7,840 pt，以及跳到第 0 轮时视口内没有字形。恢复修正后同一检查通过，确认新断言能捕获本次问题。
- 用本机 5 份真实会话的只读副本通过完整 `AppShell` 做页面切换和逐轮翻阅（分别为 3、18、7、1、7 轮），相同高度检查全部通过；长 HTML、公式和图片继续显示。测试不修改原会话，不调用模型 API，也不将内容加入仓库。可通过 `NOMI_CHAT_PERF_DATA` 指定本机数据目录，`NOMI_CHAT_PERF_OUTPUT` 可选地导出截图和布局诊断。
- 真数据检查每份总耗时约 0.60–2.24 秒，**包含每份 500 ms 的固定等待和每轮 80 ms 的人为等待**，不是应用打开延迟或帧率测量。当前没有宣称已达到某个固定 FPS。
- 前后端重新打包、签名检查通过，已重启 `Nomi-sub/build/Nomi.app`。自动化能读取 Meetings 窗口，但进入 Chat 后读取控件树仍超时；因此不把实际窗口的自动化检查算作通过，也不把工具等待时间当作主线程卡顿测量。真实数据的独立 `AppShell` 渲染截图及布局检查与此分开记录。

### 邻近消息预加载的追加验证

- 200 轮历史首次显示时，视口上方 6 轮已有原生视图及实际行高，不需要先滚动到那里才创建；含预备行的原生回答文本视图约 16 个，预备缓存最多 8 轮，没有创建完整的 200 轮历史。
- 在下一轮放置 HTML 图示，不滚动到该轮也能启动网页并测得真实高度；仍遵守最多 3 个 WKWebView 的限制。测试对 WebKit 首次异步启动采用条件等待、最长 2 秒，这不是承诺所有网页都能在某个固定毫秒内加载。
- 从底部先上移 40 pt，再连续上移 180 pt，共 9 步：进入的轮次必须已准备，首帧视口必须有字形；每步后继续让预加载与高度更新运行，首个可见轮次及行内偏移必须保持，允许误差不超过 2 pt。视图交接后还核对轮次正文，避免缓存被当作别的消息复用。
- 同一滚动检查额外连续运行 3 次通过；还检查窗口变窄后的排版，以及反复跳到远处轮次时消息视图缓存不随历史翻阅持续增长。
- 5 份本机真实会话继续通过逐轮翻阅及文本高度检查。上述检查针对本次滚动回退问题，不把人为等待计入应用延迟，不宣称固定 FPS。

### 官方资料与取舍

- [Apple：惰性列表布局、预取和滚动](https://developer.apple.com/videos/play/wwdc2026/321/) 说明离屏高度采用估算，并提醒出现后再改变布局会降低滚动可靠性。本应用的网页、图片、公式均会改变行高；采用原生复用列表是针对本项目检查结果的选择，不是声称所有 LazyVStack 都不适用。
- [Apple：NSTableView 行高委托](https://developer.apple.com/documentation/appkit/nstableviewdelegate/tableview(_:heightofrow:)) 要求高度变化通过 `noteHeightOfRows(withIndexesChanged:)` 失效缓存。本实现合并这些更新，并按轮次 ID 恢复阅读位置。
- [Apple：创建高性能可滚动堆叠](https://developer.apple.com/documentation/swiftui/creating-performant-scrollable-stacks) 建议用 Instruments 核实视图加载成本。后续若还有具体卡顿，再针对实际输入采样，而不是扩大常驻网页数量或占满空闲内存。
