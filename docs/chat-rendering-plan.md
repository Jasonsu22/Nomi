# Nomi 聊天对话框性能优化实施计划

更新日期：2026-10-19  
代码基线：`parallel` 分支，`a177cef`  
状态：待实施；本文只确定方案，不代表性能指标已经达成。  
适用范围：独立 Chat 页面、聊天历史切换、会议详情中的聊天面板。

## 1. 方案决定

采用 **SwiftUI / AppKit 原生外壳 + 常驻 WKWebView 聊天正文 + React / TypeScript 块级渲染器**。保留原生输入框、现有模型调用和本地后端，把聊天正文的 Markdown、历史列表和滚动几何统一交给 WebKit。

这次优化的交付结果是：生成文字连续出现；输入不被生成打断；快速向上翻时内容已经提前准备；切换页面和聊天记录不重复启动整套渲染器；内容高度变化不把读者拉回底部。不能通过隐藏正文、缩减历史、停止实时 Markdown 或无限保留网页来换取这些结果。

| 层次 | 选用技术 | 职责与边界 |
| --- | --- | --- |
| macOS 外壳 | 现有 Swift 6.2、SwiftUI、AppKit | 导航、设置、历史列表、原生输入框、快捷键、窗口和权限 |
| 正文宿主 | 系统 WKWebView | 同一正文内统一排版文字、代码、公式、表格、图片与引用 |
| 正文组件 | React、TypeScript、Vite | 按块订阅更新；静态构建，不引入另一套模型状态管理 |
| 列表几何 | `@tanstack/react-virtual` v3 | 块级窗口化、动态高度、预渲染范围、阅读锚点和底部跟随 |
| Markdown | `mdast-util-from-markdown`、micromark 对应 GFM / math 扩展 | 后台解析；应用层管理稳定前缀、可变尾部和块补丁；库本身不自动提供完整流式增量协议 |
| 数学与代码 | KaTeX、Shiki | 公式、代码按块处理并缓存；高亮在后台执行，长代码先显示完整普通代码 |
| 解析执行 | Web Worker | 与 WebKit UI 线程分离；本地资源下的可用性必须通过 P1 的真实 WKWebView 验证 |
| 原生业务 | 现有 AppModel、Rust / MLX、本地存储与 API 客户端 | 模型选择、生成、上下文、检索、会话持久化继续由原生管理 |

版本在实施时锁定到通过 macOS 验证的具体版本，提交 lockfile；不使用浮动 `latest`。当前工程最低系统版本是 **macOS 26**，本轮沿用；不把“适配 macOS”写成未经验证的旧系统兼容承诺。

选择这一组合，是为了让富文本在同一排版系统内完成，同时保留现有 macOS 输入体验和业务代码。直接换成 Electron 会扩大迁移范围；继续叠加逐轮 NSHostingView / TextKit / HTML 网页的尺寸协调，也不能解决超长单轮与整页重建的成本。

## 2. 已确认的现状与本次边界

以下是代码审查结论，不是新的性能实测：

| 位置 | 现状 | 计划调整 |
| --- | --- | --- |
| `Shell/AppShell.swift` | 页面使用 `.id(model.page)`，切页会重建子树 | Chat 宿主提升到稳定生命周期，避免随页面 ID 销毁 |
| `Pages/AskView.swift` | 正文使用 `.id(session.id)`，切记录重建 transcript | 切换会话数据与视口状态，不重新加载 WebView 页面 |
| `Pages/ChatTranscript.swift` | NSTableView 复用整轮 NSHostingView；邻近预备仍以轮为单位 | 改为消息部分 / Markdown 块粒度，避免一轮超长回答占据一次巨大构建任务 |
| `Pages/AnswerBody.swift` | 有后台结构准备与缓存，但文字、公式、HTML 分属不同测量路径 | Chat 的正文由 WebKit 统一测量；保留其他页面仍使用的原生实现 |
| `Engine/ChatStreamUpdates.swift` | 约 50 ms 发布累计答案全文 | 保留完整答案语义；桥接层转换为追加补丁或显式重置，避免逐次传送全文 |
| HTML 卡片 | 已有数量受限的网页池与快照 | 新正文需要独立资源预算；不能在旧池之外无上限增加活跃网页 |

旧方案已经修复过错误文本高度造成的大块空白。该修复不能回退；此前结构性检查通过，也不能证明真实切页、生成和触控板滚动已经流畅。旧过程与结果保留在 [chat-performance.md](./chat-performance.md)。后续渲染迁移以本文为准。

本轮不改变：模型提示词、模型上下文预算、ASR / 翻译、模型下载、API 配置、录音、会议存储格式。网络首 token 时间、模型推理速度和 UI 显示延迟分别记录，不能混在一起归因。

## 3. 用户体验与性能验收

### 3.1 固定体验要求

- 生成时正文按小批次连续增加，已完成段落保持稳定；不能每个 token 重排整条回答或整个历史。
- 用户向上阅读后，新文字、图片加载、公式完成和 HTML 高度变化都不能强制拉到底部。
- 正常连续上翻时，阅读方向前方已经有真实正文与有效高度；不能先展示整屏空白，等进入视口才开始构建。
- 切出 Chat 再返回，恢复原会话、草稿和阅读位置；切到另一条记录，展示对应记录的真实内容，不能闪现上一条记录冒充新内容。
- Markdown、代码、公式在生成过程中逐步成形；只延后昂贵装饰，不等整轮结束才显示正文。
- 没有缓存的任意远距离跳转允许局部准备提示，但不能清空整个聊天面板，也不能让用户滚动后被反向拉回。

### 3.2 验收工作负载

固定脱敏数据集、固定窗口和字体，优化前后使用相同脚本；真实历史只读复制，不改用户原记录。

| 级别 | 数据 | 用途 |
| --- | --- | --- |
| 日常 | 50 轮，含中英混排、引用、图片、公式和代码 | 输入、生成、常见切页 |
| 长历史 | 500 轮，约 2 MiB Markdown；20 张图片、40 个代码块、10 个公式块、5 个 HTML 卡片分布其中 | 持续上翻、快速反向滚动、会话切换 |
| 单轮压力 | 单条 200 KiB 回答；分别覆盖未闭合代码、长段落、长列表和大表格 | 增量解析与单块成本上限 |
| 极限 | 2,000 轮、约 10 MiB 正文；包含图片、公式和 HTML | 有界资源与渐进恢复，不要求与日常冷打开耗时相同 |

每组生成回放至少持续 60 秒，分别按 20 / 60 次每秒推送，并增加短时突发批次。既测试累计全文，也测试真正的 delta；生成同时进行打字、滚动和切页。远程图片下载耗时单列，不成为文本可见的前置条件。

### 3.3 指标与测量口径

下列是 **发布门槛目标**，不是当前已测结果。P0 记录实际测试 Mac 的芯片、内存、系统版本、屏幕刷新率、窗口、低电量模式，以及是否同时运行本地模型。日常和长历史必须在指定基准机上达标；本地模型运行场景另列结果，不用空载数字代替。

| 指标 | 门槛目标 | 起止与判定 |
| --- | --- | --- |
| 流式可见延迟 | p95 ≤ 50 ms，p99 ≤ 100 ms | 原生收到可显示文字，到对应文字进入可见 DOM 并经过绘制机会；另以录屏 / 系统跟踪抽查实际显示 |
| 输入响应 | p95 ≤ 50 ms，p99 ≤ 100 ms | 原生输入事件到输入框显示；覆盖中文输入法组合输入 |
| 返回原 Chat 页面 | p95 ≤ 100 ms | 导航事件到原阅读位置的真实文字可见且可滚动 |
| 热缓存切换记录 | p95 ≤ 150 ms | 选择记录到目标视口真实文字可见且可交互；不能只计骨架出现 |
| 长历史冷切换 | p95 ≤ 500 ms | 渲染器已启动、目标会话无解析缓存；只准备目标首屏，不等待全历史 |
| 应用首次 Chat | p95 ≤ 1 s | 冷启动正文宿主到首屏可读；与应用及模型启动耗时分开 |
| 连续滚动 | 60 Hz 下帧间隔 p95 ≤ 20 ms；交互期间无应用渲染工作导致的连续 > 100 ms 停顿 | 触控板每秒约 3 个视口，持续 10 秒并反向；系统合成帧与 JS rAF 分别记录 |
| 预加载空白 | 连续滚动场景中，无由未准备正文导致的整屏空白持续 > 1 个刷新周期 | 用带正文标记的逐帧画面确认，不用非空容器或占位框判定 |
| 阅读位置稳定 | 静止阅读时异步内容更新后锚点偏差 ≤ 2 CSS px；滚动中不产生反向补偿跳动 | 比较块 ID 与块内偏移，不比较文档总高度 |
| 长任务 | 常规生成和热切换不产生单次 > 50 ms 的正文主线程任务 | 使用 Web Inspector / Instruments；不依赖 WebKit 未实现的 Long Tasks API |
| 资源有界 | 热身后连续切换 20 个会话三轮，无逐轮增长趋势；缓存遵守第 9 节预算 | 同时观察 Nomi、关联 WebContent 与媒体资源；不只看主进程 RSS |

120 Hz 屏幕另外记录 8.3 ms 帧预算下表现；不能用 60 Hz 合格宣称已达到 120 Hz 满帧。p95 / p99 需有足够事件样本；切换指标至少 100 次采样。未达标先定位和调整，不用加长节流、隐藏内容或放宽数据集掩盖。

## 4. 生命周期和数据架构

```text
现有模型 / API / 检索
        ↓
原生会话数据（唯一事实来源）── 原生输入框与会话草稿
        ↓ 有序事件与补丁，带会话 / 请求 / 版本标识
常驻 ChatWebCoordinator → WKWebView 中的会话存储
                                 ↓
                          后台 Markdown 解析
                                 ↓ 块级结构补丁
                    React 块组件 + 单一列表几何管理
                                 ↓
                         文本 / 图片 / 公式 / 卡片
```

### 4.1 宿主生命周期

1. `ChatWebCoordinator` 由稳定的原生应用层持有，不属于 `.id(model.page)` 或 `.id(session.id)` 的生命周期。
2. 独立 Chat 使用一个常驻正文 WKWebView；会话切换不执行 `loadHTMLString`、页面 reload 或重建 React root。
3. 原生输入框保留；草稿、附件、输入焦点意图按会话存储，不能随 AskView 重建丢失。正文刷新不夺走输入法焦点。
4. 会议聊天使用相同渲染器与协议。当前仅一个聊天正文可见时复用宿主；如果存在同时显示的独立 Chat 与会议聊天，最多另建一个宿主，各有独立 surface ID，不能把同一 NSView 同时挂到两个父视图。
5. 隐藏页面保存视口与尺寸，暂停布局和高亮；原生继续接收生成，返回时一次补到最新版本。隐藏导致的 0 高度不能覆盖有效测量缓存。
6. 不为每个历史会话保留一棵完整 DOM；仅当前会话挂载正文，最近会话保留结构与尺寸缓存。

### 4.2 桥接协议

- 协议版本和每次渲染器启动的 epoch 明确；事件包含 surface、session、turn、generation、revision、sequence 与类型。
- 原生到正文：初始化 / 激活会话、追加文字、重置当前答案、更新引用、结束 / 错误 / 取消、主题与宽度、定位块。正文到原生：ready、确认序号、用户动作、视口锚点、渲染诊断。
- 当前接口可能给累计全文。业务层在已有文本容器追加时优先产生 delta；兼容路径只对当前回答校验前缀后提取追加部分。发生前缀改写时显式 reset，不能误当追加。全文兼容比较的成本也纳入测量，不把它称为常数时间。
- 带起始偏移与 revision 的 delta 可检测丢包、重复、乱序。原生与 JS 统一以 UTF-16 码元定义偏移，不能将 Swift 字符数与 JS 字符串下标混用。
- 一个 surface 最多一个在途发布批次，合并后续可合并追加；不无限堆积 `evaluateJavaScript`。大量历史采用分块快照，避免主线程一次 JSON 编码 / 解码全历史。
- 普通流式发布以 16–33 ms 小批次为初始值，根据实测调优；不得在已有 50 ms 节流后再无条件增加同等等待。目标是有界 UI 延迟，不是固定追求每 token 一帧。
- 最终答案由原生权威全文核对并立即完成 flush；停止、错误、切会话、WebView 重启后的旧回调全部检查代次。切到其他记录不自动取消后台生成。
- 队列积压时可合并未发布的中间状态，不能丢字符、打乱工具事件或跳过最终状态。原生存储不依赖网页确认才落盘。

## 5. 流式 Markdown 渲染

### 5.1 稳定前缀与可变尾部

后台解析器保存当前答案原文、AST、源位置与稳定块 ID。新文字到达时，只重解析可能受影响的尾部；已稳定块保持对象与组件身份。React 历史块不订阅整个答案字符串，更新通过按 ID 的选择器下发。

“稳定”必须依据语法确定，不能简单看到两个换行就冻结：Setext 标题、表格分隔线、列表续接、引用定义与脚注都可能影响前文。维护依赖关系，后出现的定义只使依赖块失效；必要时后台做全文校验。结束后与标准完整解析结果比对，只替换确实变化的块，不整条卸载重建。

- 开放代码围栏：追加代码文本，先展示可读代码，不反复解析所有已完成围栏。
- 超长未闭合段落 / 列表 / 表格：解析任务支持过期取消与最新版本优先；若不能在预算内完成，正文先追加安全的文本表现，再补局部语义。不能让旧全文解析任务排队阻塞新文字。
- 链接、强调、数学边界未闭合时保持合法、可读的临时表现；不补写到用户原文。语义闭合后即时升级展示。
- 已闭合公式及时显示；长公式后台预处理和缓存。任何 DOM 排版仍发生在 WebKit UI 线程，须实测单块成本，不能声称 Worker 消除了所有布局成本。
- 代码高亮只影响当前可见和预渲染块。后台计算 token 并缓存，按需加载语言；未知语言显示普通代码，完整复制内容不受影响。
- 原始 HTML 默认不作为正文执行；明确的演示卡片走第 8 节专门通道，不能把脚本源码作为生成预览闪出来。
- 文件导出复用结构结果、按内容变化在后台进行；不每个 token 扫描磁盘或重复导出全部历史。

### 5.2 解析执行的 macOS 验证门槛

本地资产由 WKURLSchemeHandler 提供，Worker 使用打包后的自包含脚本。**自定义 scheme、Worker / Blob、模块加载、CSP 与资源路径必须在目标 macOS WKWebView 中验证，不能用 Chrome 能运行代替。**

如果 WebKit 的本地来源限制阻止 Worker，采用相同解析代码的无 DOM bundle，在原生串行后台 JavaScriptCore 上执行，通过结构补丁回传；不退回正文主线程全量解析，不维护两套 Markdown 语法。P1 固定一种经过验证的执行方式，后续只维护该路径。该选择是执行环境兼容门槛，整体技术栈不变。

## 6. 历史预加载与列表粒度

### 6.1 三层准备

把“取到原文”“解析完结构”“真实排版可显示”分别计时和缓存。只预先读取原文不算预加载完成。

1. 激活会话：优先传目标视口需要的轮次与块，直接显示真实内容；剩余原文与索引后台分批同步。
2. 阅读方向预备：提前解析、挂载并测量前方块；图片提前解码，代码 / 公式提前准备。任务优先级为当前可见、即将到达、反方向缓冲、空闲全历史。
3. 已读历史：复用 AST、测量与媒体缓存，不因离屏又进屏重新完整构建。

当前会话原文已在原生内存中时，不人为模拟网络分页。以后若引入磁盘分页，沿用提前加载与一次批量 prepend 协议，不能每加载一页就重建全列表。

### 6.2 预渲染范围

预备范围按 **像素距离、滚动方向、速度和实测准备耗时** 决定，不固定“前面 6 条”。初始前向范围约 2 个视口、反向约 1 个视口；高速时按 `速度 × 准备耗时 p95 + 安全余量` 扩大，前向初始上限 6 个视口，并受主线程与内存预算约束。

TanStack 的 `overscan` 单位是 item 数；像素策略通过外部预加载控制器和 `rangeExtractor` 实现，不能把它误写成库自带的像素 overscan。静止时收缩，方向反转时保留必要的旧缓冲，避免反复销毁。

每次主线程预备任务初始预算 ≤ 4 ms，超出时让出执行；解析、高亮、图片准备放后台。前向缓存不足时先减装饰成本、提高准备优先级，不临时给目标区放一个巨大的空白占位。

### 6.3 块级窗口化

- 虚拟行是用户消息、助手 Markdown 块 / 工具组 / 媒体卡、轮次操作区。稳定键来自持久 turn ID 与稳定 block ID，不使用数组下标或随机 UUID。
- 持续追加只改变当前尾块；不因新 token 重建历史行索引。块闭合后只追加新行或更新受影响部分。
- 已挂载邻近行使用普通文档流与顶部 / 底部占位，不对每段正文分别做绝对定位，降低动态高度时重叠与空白风险。
- 一个特别长的代码块先限制高亮复杂度，完整文本仍可读、可复制；需要内部行窗口化时单独实现选区和复制，不能直接裁掉正文。大表格保留语义与横向滚动，不强行拆成破坏表头关系的碎片。
- `content-visibility` 仅作为验证后的局部增强，不再叠加另一套高度估算或滚动补偿；它不能代替 React 更新隔离或有界 DOM。

## 7. 单一滚动与尺寸管理

### 7.1 唯一几何所有者

Chat 正文内部只有一个主滚动容器。由 TanStack Virtual 负责测量、上方内容变化补偿与底部锚定；阅读状态控制器只决定政策，不再单独按 `scrollHeight` 差额重复补偿。外部原生视图只提供视口大小，不根据文档高度伸展窗口。

选定版本验证 `anchorTo: 'end'`、`followOnAppend`、测量快照及相关 API 后使用其能力；浏览器自动锚定在该容器关闭，避免与虚拟器同时调整。如果锁定版本缺少必要能力，先固定有该能力且通过验证的版本，不能悄悄叠加第二套补偿。

### 7.2 阅读状态

| 状态 | 触发 | 新内容到达 |
| --- | --- | --- |
| 跟随最新 | 初次打开新会话、用户明确点击回到底部 | 保持底部锚定，无逐 token 平滑滚动动画 |
| 阅读历史 | 用户向上滚动、拖动滚动条、键盘离开底部 | 不追随；显示轻量“有新内容”入口 |
| 定位中 | 搜索 / 历史跳转 / 会话恢复 | 预备目标区后定位；用户一旦主动滚动立即取消程序定位 |

用户主动上翻立即解除跟随，不能用宽泛的“离底部 80 px”把小手势吞掉。最终到达底部或显式点击入口才恢复跟随。切会话分别恢复各自的状态。

### 7.3 高度与锚点

- 阅读锚点记录 `{sessionID, blockID, 块内偏移, following}`；恢复时使用有效尺寸快照，不只保存裸 scrollTop。
- 高度键包含块内容 revision、有效正文宽度、字体 / 字号、渲染器版本与会影响排版的主题 / 样式。宽度变动不复用旧换行高度；纯颜色变化不盲目清空全部高度。
- 动态高度采用同一测量通道；同一 item 不同时交给 `measureElement` 和手动 `resizeItem`。批量更新在一次布局事务中发布，避免反复读写 DOM 触发同步布局。
- 图片尽可能保存自然宽高 / 比例，加载前占据合理空间；公式和 HTML 高度改变时保留当前可见块位置。
- 用户拖拽选择文字期间，临时固定涉及的已挂载块，防止离屏回收破坏选区；设有界保护并在结束后释放。

## 8. 图片、HTML 与富内容

普通图片后台解码、按显示尺寸下采样、预取与缓存；失败时局部提示，不阻塞其余正文。引用、链接、代码复制、文件打开 / 导出继续走原生受控动作。

HTML 演示保留内联交互能力，但不为所有历史卡片永久运行脚本：

- 普通卡片先显示已有快照或有尺寸的局部预览；视口附近提前准备；最多 1 张处于活跃交互状态，其余可点击激活。初始化预算不足时不抢占正文首屏。
- 演示作为独立文档，使用不同来源与 sandbox，默认只给予所需脚本权限，不授予原生业务桥。不能将生成 HTML 放入可信正文主页。
- 不依赖 `srcdoc` 内部 CSP 去放宽父页面 CSP；使用独立演示文档的策略和允许来源。桥接只接收验证过的来源、卡片能力 ID、代次和尺寸消息。
- 离屏暂停 / 回收，隐藏页停止演示更新；快照不等于保留 JS 表单和动画状态，回收后的状态恢复范围需明确。
- **iframe 不保证单独线程或进程；多个 WKWebView 也不保证独立 WebContent 进程。** 任意无限循环或恶意脚本不属于正文流畅度保证。此类卡片应被限制 / 终止并允许在独立预览中打开，不能宣传 sandbox 能隔离 CPU 阻塞。
- 原生 watchdog 与 WebContent 终止回调可重建宿主，并从原生答案与锚点恢复；不能因为恢复而重复向模型发送请求。

## 9. 缓存、资源与后台任务预算

以下是初始驱逐预算，P0 测量后调整；缓存成本估算不等于 WebKit 进程总内存上限。

| 资源 | 初始约束 | 失效 / 释放 |
| --- | --- | --- |
| 正文 WKWebView | 主 Chat 1 个；确有同时展示需求时会议面板再 1 个 | 不按会话增加；页面隐藏暂停工作 |
| 已解析会话 | 当前会话必要块固定；最近 3 个会话可淘汰缓存，非当前 AST 合计预算 32 MiB | 按内容版本和渲染器版本失效；内存压力优先清非当前 |
| 行高 / 视口 | 最近 10 个会话，最多 10,000 个块的测量记录 | 布局键改变清相应项，不在隐藏时写入 0 |
| 解码图片与卡片快照 | 合计 64 MiB 成本预算，单图按显示分辨率处理 | LRU、内存压力、资源删除 |
| Markdown / 高亮执行 | 每个可见 surface 最多 1 个活动解析任务，后台预取共享低优先级队列 | 当前尾部 / 可见区抢占；过期任务取消 |
| 桥接 | 每 surface 最多 1 个在途发布批次 | 确认后续发；超时重同步，不无限排队 |

当前极长会话无法完全放进预算时，只保留原生权威原文、块索引与邻近 AST，其他部分渐进准备。最近会话 cache 不保留无限 DOM / iframe。应用退出不要求新增一套磁盘 AST / 截图存储协议；本轮优先进程内缓存与现有会话文件兼容。

切换到生成中的其他会话时提高其优先级。不可见会话只维护原生正文和必要状态，不以相同频率计算 DOM、公式、高亮和 HTML 高度。

## 10. macOS 集成、构建与兼容

- Vite 只用于构建。JS、CSS、字体、公式资源和 Worker 全部打进 `.app`；发布版不需要 Node、开发服务器、额外 localhost 端口或 CDN。
- 静态资源走本地资源处理器；保持资源目录结构，避免 SwiftPM `.process` 改变路径导致模块、字体或 Worker 404。构建脚本增加确定性的前端产物步骤与清单校验。
- 生产环境使用 CSP，禁用 Markdown 任意 HTML 执行；渲染桥只允许复制、引用、资源打开等白名单动作，校验 schema、大小、来源与代次。API 密钥、任意文件路径和执行命令能力不进入网页。
- 主题、字号、本地化、减少动态效果由原生传入 CSS 变量与语言状态。遵循当前浅色 / 深色 / 跟随系统，不额外重做外观设置。
- 保留原生输入框的中文输入法、组合输入、粘贴 / 拖放图片、附件、发送 / 停止、草稿恢复和快捷键；页面切换不强制聚焦输入框。
- 验证文字选择、右键、链接、引用、VoiceOver、键盘导航、缩放和高对比度。虚拟列表需要声明完整集合位置；查找与复制全文从数据模型读取，不局限于当前 DOM。
- WebContent 崩溃恢复只恢复显示，不改写原会话或重复生成。发生渲染异常时可通过内部开关切回原生正文，同一原生会话数据始终可用。

## 12. 验证方式与完成清单

### 12.1 功能检查

- [ ] 普通 Markdown、GFM 表格 / 列表 / 引用、行内与块公式、中英混排、链接与脚注。
- [ ] 每个语法边界分割输入，累计全文改写、最终修正、停止、错误、切记录、迟到消息均正确。
- [ ] 大代码、大段落、长列表、大表格不阻塞原生输入；无法高亮时仍有完整代码正文。
- [ ] 引用、代码复制、选择文字、右键、图片预览、文件导出与范围选择保持原行为。
- [ ] 原生中文输入法组合期间更新正文和切页，不错误发送、不丢组合文本。
- [ ] 会议嵌入聊天与独立 Chat 均可用；不存在同一 WebView 同时挂载或重复生成。
- [ ] 缩放 / 改宽度 / 改主题 / 动态内容增长后无错误高度和串用缓存。

### 12.2 流畅度流程

- [ ] 生成长回答时持续输入中文和英文，穿插选择文本、复制、停止与继续新提问。
- [ ] 500 轮历史从底部连续上翻 10 秒，反向返回，滚动条远距离跳转，检查逐帧真实正文。
- [ ] 静止阅读中间历史，尾部继续生成；图片、公式和卡片陆续变高，阅读位置保持。
- [ ] Chat → Sources / Meetings → Chat，随后在不同长度的聊天之间连续切换；测热缓存与冷缓存。
- [ ] 隐藏 Chat 后继续生成，再返回；只补缺失状态，不重播每个中间 token。
- [ ] 本地模型运行时重复关键流程；监控 CPU、内存压力和 WebContent，不把推理抢占隐藏掉。
- [ ] 三轮各切换 20 个会话，观察 DOM、网页、图片与解析任务有无持续增长。

性能诊断标记覆盖：native-receive、bridge-publish / ack、parse-start / end、block-commit、measure、viewport-ready。不同进程的时钟先对齐；rAF 与 DOM 标记是绘制机会的近似，不能当作屏幕已经显示的证明。实际画面通过录屏 / 系统跟踪确认。

不要在计时区间用整页 Accessibility 树扫描或高频截图拖慢被测应用。自动回归先检查协议、字形 / 内容标记和锚点，真实 AppShell 中再做少量必要交互回放。编译、前端浏览器检查、macOS 宿主验证和性能测量分别报告。

- [ ] P0–P6 有对应记录，而非仅有“已优化”描述。
- [ ] 指标报告给出基线、新结果、样本量、硬件、工作负载与失败项。
- [ ] 定义中的空白与跳位案例已经用真实正文 / 逐帧画面排除。

- [ ] 依赖版本与许可证检查完成，未误引入商业虚拟列表授权要求。

## 13. 主要风险与处理决定

| 风险 | 处理 |
| --- | --- |
| WebKit 本地来源下 Worker / 模块加载受限 | P1 先验证；不通过则使用同一解析 bundle 的后台 JavaScriptCore 执行，不能延后到大规模迁移后发现 |
| 增量 Markdown 边界判断错误 | 标准解析器对照与碎片化输入样例；允许依赖块重算，保留最终全文校验；不承诺任意输入每次 O(1) |
| 动态高度与预加载互相争抢滚动 | 虚拟器唯一几何所有者；阅读政策不另算高度差；真实 WKWebView 验证反向滚动 |
| 重量级 HTML 挤占 UI | 限制活跃实例、快照 / 预览与原生恢复；不把 iframe 当 CPU 隔离方案 |
| WebKit 带来常驻内存成本 | 只保留有界宿主和数据缓存；同时测原生与 WebContent，总收益必须由 P6 对比确认 |
| 只做窗口化导致全文选择 / 查找 / VoiceOver 退化 | 数据驱动全文动作、选区保护、语义标记和辅助功能验证作为切换门槛 |
| 新旧实现共存引入双重状态 | 原生数据唯一事实来源；网页可销毁恢复，不改变持久化协议；回退不迁移数据 |

## 14. 调研依据与证据边界

本文的技术选择是针对 Nomi 现有结构的工程决策，不代表已经证明其速度优于所有其他方案。公开项目提供可核对的实现方法；Codex Cloud、Gemini、Kimi 网页和 DeepSeek 网页的内部渲染实现并未全部公开，不能凭使用体验推断它们用了相同技术栈。

1. **DeepSeek Harness：增量解析与稳定块。** 可查看固定提交的 [incremental.ts](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/ui-primitives/src/markdown/incremental.ts) 与 [MarkdownText.tsx](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/packages/client/ui-primitives/src/markdown/MarkdownText.tsx)。它们提供冻结稳定结构、处理可变尾部与复用组件的实例；不等于 DeepSeek 消费者网页的源码，也不意味着任意 Markdown 都可常数时间处理。
2. **DeepSeek Harness：导航与历史批次。** [导航性能设计](https://github.com/deepseek-ai/deepseek-harness/blob/687f282e8625c6b8d11ff58211a90524be2e4317/.agents/notes/archived/architecture/2026-09-18-chat-navigation-performance.md) 区分视口几何、阅读政策与历史导航，值得借鉴。文档涉及的虚拟化不能泛化为整个主聊天正文都已经虚拟化。
3. **Kimi Code：分离昂贵装饰。** [Markdown.tsx](https://github.com/MoonshotAI/kimi-code/blob/5710c5496a213742ca0687f69dd8eeb5bde52dbf/apps/vscode/webview-ui/src/components/Markdown.tsx) 展示 memo、Markdown / math 与可控制的 enrichment。它属于公开 VS Code UI，不能据此断言 kimi.com 的内部方案。
4. **assistant-ui：长对话的窗口化粒度。** [Thread Virtualization](https://www.assistant-ui.com/docs/guides/virtualization) 讨论 content-visibility、消息部分粒度与滚动协调。本文据此采用更细块索引，但不引入 assistant-ui 的整套会话运行时。
5. **TanStack Virtual：动态列表能力。** [Virtualizer API](https://tanstack.com/virtual/latest/docs/api/virtualizer) 与 [Chat 示例](https://tanstack.com/virtual/latest/docs/framework/react/examples/chat) 是测量、稳定键、底部锚定、跟随、尺寸快照和范围控制的依据；实施必须锁定并验证对应版本。
6. **Markdown 标准解析底座。** [mdast-util-from-markdown](https://github.com/syntax-tree/mdast-util-from-markdown) 提供 Markdown 到 mdast 的解析与扩展入口；本文的稳定块协议和依赖失效仍是应用要实现的部分。
7. **浏览器离屏优化。** [web.dev：content-visibility](https://web.dev/articles/content-visibility) 解释跳过离屏渲染及尺寸估计；它不消除全量 React 更新，也不保证估计高度正确。
8. **macOS 原生宿主。** [Apple：WKURLSchemeHandler](https://developer.apple.com/documentation/webkit/wkurlschemehandler) 用于应用自定义资源加载；Worker、脚本策略和打包资源组合的兼容性仍须在目标宿主实测。
9. **产品层参考。** [Gemini Canvas 官方说明](https://support.google.com/gemini/answer/16047321?hl=en) 可用于理解聊天与产物预览的交互分工，不作为其内部进程隔离、虚拟化算法或性能指标的证据。
